Bluetooth: Huawei FreeBuds no longer connect - BR/EDR signalling-MTU check discards vendor frames

Since a recent noble kernel update Huawei FreeBuds 3 pair successfully but never
finish connecting. The ACL link comes up, authentication and encryption succeed,
and the earbuds tear the link down about 160 ms later with reason 0x13 (Remote
User Terminated). The cycle repeats every 3-4 seconds and never converges - 36
consecutive attempts over four minutes in my testing.

ROOT CAUSE

The earbuds send battery telemetry as a 68-byte L2CAP Echo Request on the
signalling channel:

    <--  L2CAP Echo Request    ident=129 len=64
         payload: "AT+HUAWEIBATTERY=6,2,100,3,0,4,100,5,0,6,35,7,0\r"
    -->  L2CAP Command Reject  reason=1 (Signalling MTU exceeded) max_mtu=48

The noble tree carries the commit "Bluetooth: L2CAP: reject BR/EDR signaling
packets over MTUsig" (Michael Bommarito, author date 2026-09-03), which adds
L2CAP_SIG_MTU (48) to include/net/bluetooth/l2cap.h and makes l2cap_sig_channel()
discard any signalling packet above it:

    if (skb->len > L2CAP_SIG_MTU) {
            u8 ident = skb->data[1];

            BT_DBG("signaling packet exceeds MTU: %u > %u",
                   skb->len, L2CAP_SIG_MTU);
            l2cap_sig_send_mtu_rej(conn, ident);
            goto drop;
    }

The Echo Request therefore never reaches the L2CAP_ECHO_REQ handler and no Echo
Response is sent. The device waits for it, stalls, and disconnects.

Vanilla 6.8, 6.12 and 6.15 do not contain this check, so this is specific to
trees carrying that commit.

HCI level, showing that the crypto side is fine and the remote simply hangs up:

    Connect Complete      status=0x00
    Link Key Request
    Auth Complete         status=0x00
    Encryption Change     status=0x00 enabled=1
    ...
    Disconnect Complete   status=0x00 reason=0x13 (Remote User Terminated)

IMPACT

Bluetooth audio hardware that worked on earlier noble kernels stops working after
a routine kernel update, with no error visible to the user - the device simply
never connects. The failure mode gives no hint that a kernel change is
responsible.

VERIFICATION

Rebuilding only bluetooth.ko with L2CAP_SIG_MTU raised from 48 to 672 restores
normal operation: the earbuds connect on the first attempt, A2DP comes up, and
the link has been stable since. No other change.

SUGGESTED HANDLING

The device is out of spec - Bluetooth Core 5.4, Vol 3, Part A section 4 puts
MTUsig at 48 octets - so the commit is correct as written. But discarding the
whole packet regresses working hardware. Continuing to process commands that fit
within MTUsig, or answering Echo Requests regardless of size, would keep
interoperability. At minimum this deserves a release-note mention, since affected
users have no way to connect the symptom to the kernel.

ENVIRONMENT

  Ubuntu 24.04, kernel 6.8.0-147-generic (also reproduced on 6.8.0-146-generic)
  BlueZ 5.72, PipeWire 1.0.5
  Intel AX201, firmware ibt-17-16-1 155-35.23
  Huawei FreeBuds 3
  Control: JBL TUNE770NC connects and plays normally on the same host
